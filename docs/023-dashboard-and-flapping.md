# 023 · 대시보드와 경보 깜빡임

측정일 2026-09-22. [020-manufacturing-scope.md](020-manufacturing-scope.md) Phase 2 마무리.

[021](021-opcua.md)·[022](022-fdc-detection.md) 에서 "Docker 가 올라오지 않아 미측정" 으로
남겨둔 것들을 전부 확인했고, 그 과정에서 유닛 테스트가 못 잡은 결함 하나를 찾았다.

## 화면

사이드바에 **이상 감지** 패널, 추이 영역에 **설비 센서** 차트를 더했다.

경보 항목에 **어느 탐지기가 올렸는지를 같이 띄운다.** 이게 요점이다 — 이동 통계가 올린
`순간 이상` 과 EWMA 가 올린 `추세 이탈` 은 현장 대응이 다르다. 전자는 확인, 후자는 정비
계획이다. 방식을 감추면 "경보가 떴다" 이상을 말해주지 못한다.

| 표시 | 탐지기 | 뜻 |
|------|--------|-----|
| 한계 초과 | `THRESHOLD` | 절대 넘으면 안 되는 선을 넘었다 |
| 순간 이상 | `MOVING_SIGMA` | 한 점이 튀었다 |
| 추세 이탈 | `EWMA` | 기준선에서 벗어나 유지되고 있다 |

센서 차트는 **채널 목록을 코드에 박지 않고 서버에 묻는다**
(`GET /api/history/sensor-channels`). OPC UA 쪽은 브라우징으로 채널을 찾아오므로,
설비가 채널을 늘리면 백엔드도 화면도 손대지 않고 탭이 하나 늘어난다.

y축은 0 기준이 아니라 데이터 범위에 맞춘다. 베어링 온도 45℃ 를 0 부터 그리면 변동이
선 두께에 묻혀 아무것도 안 보인다.

상단 지표에서 **설비알람**과 **이상감지**를 나눠 센다. 설비가 스스로 보고한 알람
(`status=ALARM`) 과 FDC 가 통계로 찾아낸 경보는 다른 것이다.

## 미측정으로 남았던 것 — 전부 확인

compose 전체 기동(`BACKEND_PORT=8082 docker compose up -d`) 후 실측.

### Flyway 마이그레이션

```
version |    description    | success
--------+-------------------+--------
 1      | pre-flyway schema | t
 2      | equipment source  | t
 3      | sensor and fdc    | t
```

### 두 프로토콜이 한 테이블로 합류

2분 구간 `equipment_state_log`:

| source | 행 수 |
|--------|-------|
| MQTT | 192 |
| OPC_UA | 124 |

`equipment_sensor_log` 도 같다 — 채널 3개가 프로토콜 양쪽에서 들어오고 평균이 공칭값과
맞는다(MotorCurrent 12.00 / 12.01, BearingTemp 44.97 / 45.00, VibrationRms 2.51 / 2.65).

### OPC UA 수집

```
OPC UA 연결 opc.tcp://simulator:4840/fleetdeck/server/ - 설비 2대, 변수 18개, 모드 SUBSCRIBE
OPC UA 구독 생성 - 모니터 항목 18개, publishing 1000.0ms
```

설비 2대 × (상태 6 + 센서 3) = 18. **센서 채널을 백엔드에 이름으로 박지 않았는데 들어왔다.**

### 정답 라벨과 탐지의 왕복

```
 kind     | phase | equipment_id | channel
----------+-------+--------------+--------------
 VARIANCE | START | UA-SORTER-02 | VibrationRms
 VARIANCE | END   | UA-SORTER-02 | VibrationRms
```

주입 → 라벨 적재 → 탐지 → 경보 적재 → 화면까지 한 바퀴가 닫혔다.

## 유닛 테스트가 못 잡은 결함: 경보 깜빡임

위 VARIANCE 이상 **1건에 EWMA 경보가 8번** 올라왔다.

원인은 `AlarmSuppressor` 가 **정상값 하나에 바로 해제**하던 것이다. 산포가 커지는 고장은
값이 관리한계를 오르내린다. 올라가면 경보, 한 점 내려오면 해제, 다시 올라가면 또 경보 —
막으려던 chattering 이 **해제 쪽에서** 그대로 났다.

유닛 테스트는 전부 통과하고 있었다. 위반이 이어지는 경우와 정상으로 돌아오는 경우는
따로 검증했지만, **오르내림을 반복하는 입력을 넣어보지 않았다.**

### 고친 방법: 올릴 때와 내릴 때의 조건을 다르게

| | 조건 |
|---|---|
| 올리기 | 연속 `raiseAfter` 회 위반 |
| 내리기 | 연속 `clearAfter` 회 정상 |

탐지기마다 다르게 준다. 억제 방식을 방식마다 다르게 했던 것과 같은 이유다.

| 탐지기 | 올리기 | 내리기 | 왜 |
|--------|--------|--------|-----|
| `THRESHOLD` | 2회 | 5회 | 오르내림에 깜빡이면 안 된다 |
| `MOVING_SIGMA` | 1회 | **1회** | 단발 이상은 하나하나가 별개 사건이다. 해제를 늦추면 다음 스파이크를 삼킨다 |
| `EWMA` | 2회 | 5회 | 추세 이탈은 상태다 |

### 결과

3분 관측, 이상 3건(DRIFT / STEP / SPIKE) 주입:

| 탐지기 | 경보 수 |
|--------|--------|
| `MOVING_SIGMA` | 10 |
| `EWMA` | **4** |
| `THRESHOLD` | 1 |

EWMA 가 이상 1건당 8회에서 **이상 3건에 4회**로 떨어졌다. `MOVING_SIGMA` 의 10 은 의도한
것이다 — 해제가 즉시라 단발 이상을 하나씩 센다.

## 남은 것

- **운영 데이터 위에서의 채점.** `sensor_alarm_log` × `fault_injection_log` 를 맞추면
  [022](022-fdc-detection.md) 의 오프라인 채점을 운영 중에도 할 수 있다. 쿼리를 아직 안 짰다
- **채널별 억제 설정.** 지금은 `ChannelMonitor` 에 상수로 박혀 있다. 022 의 결론대로면
  진동처럼 순간값이 중요한 채널과 온도처럼 느린 채널은 설정이 달라야 한다
- **구독 vs 폴링 부하 비교.** 스택은 이제 뜨므로 모드만 바꿔 재면 된다
- **단절 후 재구독 복구 시간.** 코드만 있고 실측이 없다
- README 의 대시보드 스크린샷이 이전 화면이다
